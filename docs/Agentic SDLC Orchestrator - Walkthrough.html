01 — The assignment

What was asked, and what got built.

The brief. The assessment asks for a working URL-shortener prototype built and improved with AI assistance. But the URL shortener itself is a vehicle. The document is explicit that the real subject under evaluation is the orchestration layer: an agentic system that carries a requirement through analysis, planning, implementation, testing, documentation, and release readiness with governance rather than a simple linear chain of prompts.

Eight capabilities are named directly: requirement understanding, task decomposition, codebase reasoning over an existing brownfield system, workflow orchestration, engineering output generation, validation and risk control, controlled autonomy, and a final engineering summary. Three demonstrated scenarios are required — greenfield, brownfield, and an ambiguous requirement — each showing decomposition, orchestration, and validation.

The build. agentic-sdlc-orchestrator is a Python/LangGraph application that treats a software requirement as something that has to earn its way through a governed lifecycle, not something an agent just executes. A stable control graph owns routing, retries, human interrupts, and the exit gate. A separate, per-run TaskGraph represents the actual engineering work — and that graph is data, not new LangGraph nodes, so the control plane stays reviewable while every requirement produces different work underneath it.

The checked-in evaluator material now shows one real publication lineage: 13 tests passing for the V17 greenfield baseline and 20 tests passing for its V18 brownfield expiration evolution. Ambiguity governance remains implemented and is demonstrated interactively through the live requirement-review workflow rather than through a third frozen sample.

02 — How it works

Two graphs, kept deliberately separate.

The single design choice that shapes everything else: useful, nondeterministic reasoning is kept apart from authoritative decisions. An LLM can propose an analysis or a plan. It can never decide that its own output is ready.

Control graph

The stable LangGraph pipeline

Implemented once in LangGraph: routing, bounded planning retries and revisions, human interrupts, safe-stop behavior, checkpointed state, execution-loop iteration, and the exit gate. It doesn't change shape per requirement, and the LLM never creates or rewires its nodes or edges.

Engineering graph

The per-run TaskGraph

A dynamic domain artifact. The model proposes tasks, types, dependencies, and traceability using temporary keys; application code assigns real TASK-001 identity, validates the DAG, derives layers and parallelism, and a human approves the result before anything runs.

The execution loop is bounded and serialized on purpose. At each step, the scheduler selects every task whose dependencies have already succeeded, starts that whole wave at once (capped at two tasks running concurrently), and invokes independent Task Agents in parallel threads. It then joins the wave, canonicalizes every result in deterministic graph order regardless of which one physically finished first, reconciles any same-wave file conflicts, and applies changes to the workspace one at a time. Physical completion timing never gets to change audit order or mutation order — that's decided entirely by the graph, not the race.

Every file change is a transaction, not a write. A Task Agent never touches a filesystem. It returns a proposed output; application code derives whether that output means CREATE, MODIFY, or NO_CHANGE by comparing content hashes against the current workspace snapshot, checks the target path against a policy that blocks .git, .env, traversal, and symlinks, and only then applies it — atomically, with the previous state captured for rollback. If a postimage doesn't verify, the runtime restores the prior file from the captured bytes and mode, or fails closed into ROLLBACK_FAILED rather than pretending the workspace is trustworthy.

03 — Requirements coverage

The eight core requirements, one at a time.

Each card pairs the assignment's own language with the specific mechanism that satisfies it, and where to look for evidence.

1

Requirement Understanding

Interpret intent, identify ambiguity, normalize into a clear engineering problem.

The Requirement Analysis Agent produces a structured breakdown into FR, NFR, CON, AC, RISK, and AMB items. Deterministic policy — not the model — decides READY or BLOCKED: any nonblank ambiguity forces BLOCKED with reason code UNRESOLVED_REQUIREMENT_AMBIGUITY, and a blocked analysis can only be sent back for changes or rejected — approval is refused by code, not by convention.

2

Task Decomposition

Convert high-level requirements into actionable tasks with dependencies and sequencing.

The Task Planning Agent proposes titles, types, temporary dependency keys, and a materialization policy from the approved specification alone. Application code assigns canonical TASK-001 IDs, remaps dependencies, rejects cycles and missing references, and derives topological layers and parallelism. Coverage is bidirectional and enforced: every approved FR/NFR/CON/AC item must be traced to at least one task, or the graph fails validation before a human ever reviews it.

3

Codebase Reasoning Brownfield

Identify impacted modules/services/APIs/data flows; demonstrate architectural understanding.

The brownfield scenario runs a FORBIDDEN-materialization impact-analysis task against five explicit repository files before any implementation task starts. Task Agents never browse a repository — they receive a bounded RepositoryContext of only the files their task and its dependencies are scoped to, with exact content, hashes, or explicit nonexistence.

4

Workflow Orchestration Critical differentiator

An explicit dependency graph with entry/exit gates, sequential and parallel paths with synchronization, cross-stage lineage, human approval checkpoints, bounded retries/fallback/rollback/safe-stop, policy guardrails, audit-grade observability, reliability metrics, and dynamic re-planning — all under controlled autonomy.

This is where the two-graph design (Section 02) does its work, item by item:

  • Entry/exit gates — a deterministic entry gate before analysis, and a deterministic exit gate before publication that, for runnable-project runs, additionally verifies a launch surface, tests, and root run instructions exist in the final snapshot.
  • Parallel paths with synchronization — up to two tasks run concurrently per wave; the scheduler joins the full wave before making its next dispatch decision.
  • Cross-stage lineage — every spec and graph carries a version, content hash, and optional predecessor ID; every FR/NFR/CON/AC/RISK/AMB item gets its own deterministic lineage UUID.
  • Human approval checkpoints — two real LangGraph interrupt() points (requirement review, TaskGraph review), each supporting APPROVE / REQUEST_CHANGES / REJECT with a bounded revision budget.
  • Bounded retries, rollback, safe-stop — up to three attempts per task; failed mutations roll back from captured preimages or fail closed into ROLLBACK_FAILED; unrecoverable state routes to a hard safe_stop node.
  • Governed fallback / escalation — retry classification and budgets are deterministic, and same-wave write conflicts have one explicit execution fallback: affected tasks consume retry budget and rerun as canonical singleton waves against the latest snapshot. The system never silently switches models or providers. Exhausted or non-retryable recovery safe-stops; that run does not auto-resume, so any later correction must begin another explicitly governed progression and pass the applicable revision, planning, and approval gates.
  • Policy guardrails — each task carries a human-approved FORBIDDEN / ALLOWED / REQUIRED materialization policy; a path policy independently blocks .git, .env, traversal, and symlinks.
  • Audit-grade observability — every run writes a manifest, requirement analysis, approved spec, task graph (JSON + human-readable Markdown), execution trace, workspace-mutation record, and summary to an isolated runs/<run-id>/ bundle.
  • Reliability metrics — a read-only projection over retained evidence reports success rate, retry/rollback frequency, and outcome counts per scenario; MTTR and end-to-end latency are explicitly reported as NOT_MEASURED rather than estimated.
  • Governed re-planning on upstream change — every TaskGraph is bound to the exact requirement-spec identity and version it was planned from. That authority is checked before workspace initialization and before every execution-loop advance. If it changes, STALE_TASK_GRAPH blocks the obsolete graph before request dispatch or mutation. The implementation does not synthesize or patch a replacement automatically: a new graph must be regenerated, deterministically validated, and human-approved. Dynamic engineering plans are therefore supported through governed replacement while the control topology remains stable and reviewable.
5

Engineering Output Generation

Production-quality code, API/schema definitions, tests, and documentation with clean design.

Structured deliverable roles — RUNNABLE_ENTRYPOINT, AUTOMATED_TESTS, RUN_INSTRUCTIONS — participate in TaskGraph review, execution validation, and the exit gate itself. The three generated products are dependency-free, standard-library Python projects with their own passing unittest suites and a root README covering setup, run, test, and usage.

6

Validation and Risk Control

Identify risks, trade-offs, and failure scenarios; define validation and safety guardrails.

RISK-### items are first-class, approved engineering considerations passed into task context. Every stage of the pipeline has its own deterministic validator — requirement analysis, TaskGraph DAG and coverage, task execution results, materialization intents, and workspace change sets — each producing a separate, inspectable judgment rather than one opaque pass/fail.

7

Controlled Autonomy

Agents execute multi-step work; humans provide oversight, approvals, and final quality control.

A Task Agent's return value is a non-authoritative proposal: it cannot declare success, assign an artifact ID, claim a filesystem effect, or pick CREATE/MODIFY/NO_CHANGE. Every one of those decisions is made by application code, after the fact, against evidence. Autonomy is bounded to reasoning inside a disposable, isolated workspace — never to Git, shell, deployment, or CI/CD, which stay outside the agent's authority entirely.

8

Final Engineering Summary

Plan/rationale, artifacts, risks/trade-offs/validation, assumptions, and limitations.

Delivered as ENGINEERING_SUMMARY.md: objective and rationale, a decisions table with consequences, a validation strategy, reliability and failure handling, security guardrails, explicit assumptions, a risks/trade-offs section, and a deliberately-deferred scope list. See Limitations below for the honest version of that list.

06 — Validation & guardrails

The change-control chain, narrowing at every step.

Bounded repository context → Isolated workspace → Restricted mutation vocabulary → Deterministic validation → Preimage checks → Serialized apply → Postimage verification → Rollback or hard safe-stop

Task Agents receive explicit file content, hashes, and nonexistence facts for authorized paths — never a repository handle or a "go explore" instruction. Mutation logic rejects absolute paths, traversal, symlinks, special files, duplicate targets, and protected names (.git, .env, .venv). CREATE requires proven nonexistence; MODIFY requires the exact expected preimage; NO_CHANGE verifies without writing anything. The authoritative workspace snapshot only advances after a verified APPLIED result.

None of this is presented as container- or VM-grade isolation — it's a disposable directory with a strict policy layer in front of it, which is an honest, appropriately-scoped claim for a prototype rather than an overstated one.

07 — Deliberate limitations

What this doesn't do, on purpose.

A prototype that's honest about its edges is more defensible than one that quietly hopes nobody asks. This list is reproduced from the repository's own engineering summary.

Out of scopeNo autonomous Git branch, commit, push, PR, or merge capability.
Out of scopeNo CI/CD promotion and no deployment authority.
Out of scopeGenerated code and generated tests are never executed by the orchestrator itself — readiness is evidence-based, not runtime-proven.
Out of scopeNo DELETE support, no unrestricted filesystem operations.
Out of scopeNo distributed workers, no crash-recovery journaling, no durable tamper-evident audit store.
Out of scopeNo live dependency-graph surgery or active-task migration — a stale plan is safe-stopped; any replacement must be regenerated, validated, and approved, never patched in place.
UnmeasuredMTTR and end-to-end latency are reported as NOT_MEASURED. The evidence model doesn't retain authoritative timing boundaries, and file timestamps aren't substituted for missing telemetry.
Trade-offA stable LangGraph topology is reproducible and testable, but deliberately gives up self-modifying control flow.
08 — FAQ

Frequently Asked Questions

Is this actually calling an LLM, or is it three canned demos wearing a costume?
Both paths exist, on purpose. The interactive CLI (agentic_sdlc demo / agentic_sdlc run) makes real, structured-output calls to OpenAI for requirement analysis, task planning, and each Task Agent's execution. The three checked-in reviewer bundles instead use scripted, deterministic clients so an evaluator can regenerate and inspect them with no API key and no network variability. Same governed workflow, same validation, same LangGraph routing either way — only the reasoning source changes.
How do I check this myself in a few minutes?
No credentials needed. From the repo root: .venv/bin/python -m pytest -q tests/test_workflow.py::test_successful_run_writes_canonical_artifact_set replays the greenfield path, tests/test_brownfield_demo.py covers brownfield, and python -m tests.demo_ambiguity_scenario plus tests/test_ambiguity_demo.py regenerate the ambiguity scenario. Each generated product also has its own unittest discover command in its own README.
What actually stops an agent from doing something destructive?
Several independent layers, not one. Task Agents get no filesystem, shell, or Git access at all — they return a proposal. That proposal is only realized inside a disposable, isolated workspace, after a path policy blocks dangerous targets, after a per-task human-approved materialization policy (FORBIDDEN / ALLOWED / REQUIRED) authorizes it, and after a preimage check confirms the file is in the state the change assumes. Any failure past that point rolls back from captured bytes, or the run fails closed.
Is the human approval real, or just a message that gets acknowledged automatically?
It's a real blocking interrupt. Both checkpoints use LangGraph's interrupt() and pause the graph until a Command(resume=...) is supplied. A BLOCKED requirement analysis is only offered REQUEST_CHANGES or REJECT in the review step — an attempted APPROVE is rejected by the domain code, not merely discouraged by a prompt.
What happens when a task fails?
A task gets up to three attempts total. Application code — not the model — classifies each failure as retryable or not; request-build and invariant failures are always non-retryable, while a specific allowlist of transient or correctable issues may retry with feedback about what went wrong. The implemented fallback is governed execution behavior, not model substitution: same-wave write conflicts may consume retry budget and rerun as singleton waves against the latest snapshot. Exhausted or non-retryable recovery marks the graph failed and routes to safe-stop. There is no fallback model, no silent provider switch, and no automatic resume from a safe-stopped run.
Does it really run tasks in parallel, or is "parallel" just marketing?
It's real, bounded concurrency: up to two TaskExecutor.execute() calls run in worker threads at once, and the test suite proves true overlap using thread barriers rather than inferring it from timing. Everything else — request building, validation, conflict reconciliation, mutation, settlement — stays single-threaded on purpose, so audit order can never depend on which thread happened to finish first.
How does it handle a genuinely ambiguous requirement?
See the ambiguity scenario above. "Expire URLs after a period of time" doesn't specify a TTL, a clock basis, error behavior, scope, or persistence. The analysis correctly reports needs_clarification=true, deterministic policy marks it BLOCKED, and the planner is never invoked until a human supplies the missing decisions. The system is deliberately built not to guess and quietly ship a made-up 30-day rule.
Why doesn't it just deploy the thing it builds?
That's an intentional trust boundary, not a missing feature. Filesystem mutation authority is scoped to one disposable workspace; Git, CI/CD, and deployment are treated as separate, external decisions that stay with a human. Runnable-project readiness proves the required surfaces exist — it's evidence of completeness, not a claim that the orchestrator watched the tests pass.
What's the honest weak point of this prototype?
Reliability metrics are real but incomplete by design — MTTR and latency are reported as NOT_MEASURED rather than backfilled from file timestamps. Recovery is process-local (an InMemorySaver checkpoint), so an interrupted run doesn't currently survive a process restart. And the control graph's topology is static: it governs dynamic TaskGraph data well, but it doesn't perform live dependency surgery on a running plan. See the full limitations section.
